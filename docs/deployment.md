# Render deployment and TURN setup

## 1. Why Render failed before

### `sh: 1: vite: not found`

The repository had **no `package-lock.json`** (only a `bun.lock`). Render detects
npm projects by `package-lock.json`/`yarn.lock`; without one it ran the build
command against an empty `node_modules`. The build tool was not missing from
`package.json` — dependency installation never happened.

Fixed by committing `package-lock.json` (generated by npm) and using an explicit
build command that always installs the locked tree.

### `ERESOLVE` (esbuild conflict)

The repository declared **`esbuild@^0.25.0` directly in `devDependencies`** while
`vite@8.3.5` declares an optional peer dependency `esbuild: ^0.27.0 || ^0.28.0`.
npm 7+ installs peer dependencies and refuses to resolve two incompatible
`esbuild` majors. The direct dependency was unused (nothing imports `esbuild`;
`tsx` and Vite bundle their own), so it was **removed** rather than suppressed
with `--force`/`--legacy-peer-deps`. npm now resolves `esbuild@0.28.2` for Vite.

### A third, latent failure: `tsx` in devDependencies

`npm start` runs `tsx server.ts`, but `tsx` was a devDependency. Any
production install (`NODE_ENV=production`, `--omit=dev`) would have started the
server and failed with `tsx: not found`. `tsx` is now a **runtime dependency**.
Vite is also kept in `dependencies` so the build works even on a host that
installs only production dependencies; the server imports Vite **dynamically and
only when `NODE_ENV !== 'production'`**, so production never loads it.

The Bun workaround (`bun install --frozen-lockfile && bun run build`) was **not**
used: the lockfile was removed in favour of npm, and Render's default Node
runtime does not provide Bun.

## 2. Exact Render settings

A `render.yaml` blueprint is committed. With the Blueprint flow Render applies
these automatically:

| Setting | Value |
| --- | --- |
| Runtime | Node |
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |
| Node version | `22.14.0` (`NODE_VERSION` env var + `.node-version`) |
| `NODE_ENV` | `production` |

If the service already exists and you are not using the Blueprint, set the same
values in **Dashboard → Settings**:

* Build Command: `npm ci --include=dev && npm run build`
* Start Command: `npm start`
* Environment: `NODE_ENV=production`, `NODE_VERSION=22.14.0`

`npm ci` uses the committed lockfile and fails if `package.json` and the lockfile
diverge — that is intentional. `--include=dev` is required because Playwright and
TypeScript live in devDependencies; the Vite build itself is in `dependencies`.

`npm start` runs the TypeScript Node server directly through `tsx`. It never
starts the Vite dev server when `NODE_ENV=production`; the server then serves
`dist/` and returns a clear 503 if `dist/index.html` is missing.

## 3. Environment variables

| Variable | Required | Notes |
| --- | --- | --- |
| `NODE_ENV` | yes | `production` |
| `APP_URL` | yes | Public `https://<service>.onrender.com`; used to build invite links. Health warns if missing/non-https/localhost. |
| `ULTRAVOX_API_KEY` | for AI | Server-side only. The app starts, serves `/sales`, `/join` and human audio without it; AI requests return `503 MISSING_API_KEY`. |
| `TURN_URLS` | for relay | Comma-separated `turn:`/`turns:` URLs. |
| `TURN_SECRET` | preferred auth | coturn `use-auth-secret` (TURN REST). Server mints per-session, expiring credentials. |
| `TURN_TTL_SECONDS` | optional | Lifetime of minted credentials / provider TTL request (default 3600). |
| `TURN_USERNAME` / `TURN_CREDENTIAL` | static fallback | Used when no `TURN_SECRET`/provider is set. The password is sent to authorized browsers. |
| `TURN_CREDENTIALS_URL` | managed provider | Server-side GET/POST returning temporary ICE servers. |
| `TURN_CREDENTIALS_AUTH` | with provider | Authorization header for the provider (never exposed). |
| `TURN_CREDENTIALS_METHOD` | optional | `GET` (default) or `POST` (sends `{"ttl":N}`; Cloudflare-style). |
| `STUN_URLS` | optional | Defaults to Google STUN. |
| `ICE_TRANSPORT_POLICY` | optional | `all` (default) or `relay` for verification. Relay-only fails with 503 if no usable TURN exists. |
| `MAX_SESSIONS` | optional | In-memory cap, default 500. |

Secrets are never returned by `/api/health`, never written to logs, and TURN
credentials are only served by `GET /api/sessions/:id/ice-config` to a holder of
that session's salesperson or customer credential.

## 4. TURN: what exists and what you must create

**No TURN service or credential is configured in this repository.** Code cannot
create a relay; a relay must run somewhere with public UDP/TCP ingress. Render
web services only expose HTTP(S), so coturn must run on a VPS/other host (or use
a managed provider).

Three supported modes, in order of preference:

### A. coturn with a shared secret (recommended, short-lived, self-hosted)

1. Run coturn on a small VPS with a public IP and open UDP/TCP 3478 (and 5349
   for `turns:`), configured with `use-auth-secret` and a long random `static-auth-secret`.
2. In Render set:
   * `TURN_URLS=turn:<host>:3478?transport=udp,turns:<host>:5349?transport=tcp`
   * `TURN_SECRET=<the same static-auth-secret>`
3. No long-lived TURN password ever reaches a browser: the server derives
   `username=<expiry>:<sessionId>` and `credential=base64(HMAC-SHA1(secret, username))`.

This is the only mode that has been exercised end-to-end by this repository's
HTTP/signaling tests (with mocked relay reachability). Real relay media still
requires the VPS + credentials above.

### B. Managed provider with a credentials API

Set `TURN_CREDENTIALS_URL`, `TURN_CREDENTIALS_AUTH` and, if the provider requires
it, `TURN_CREDENTIALS_METHOD=POST`. The server fetches and caches temporary ICE
servers for 5 minutes; the provider API key stays server-side.

* **Cloudflare Realtime TURN** — official docs: the TURN service is free when
  used with the Realtime SFU, otherwise **$0.05 per real-time GB** outbound to the
  TURN client. Credentials are created with
  `POST https://rtc.live.cloudflare.com/v1/turn/keys/<KEY_ID>/credentials/generate`,
  `Authorization: Bearer <TURN_KEY_API_TOKEN>`, body `{"ttl": <seconds>}`, and the
  response is `{ "iceServers": [ ... ] }`. This matches our `POST` mode. You need
  a Cloudflare account, a TURN key, and its API token.
* **Metered TURN** — the free plan is a **500 MB/month trial** (ingress+egress);
  paid tiers start at 150 GB/$99 per month. Its REST API issues/reads credentials
  (the v2 credentials *list* endpoint reports “api not available under free
  plan”, so use the credential-creation endpoint or dashboard credentials).
  Static project credentials can be placed in `TURN_USERNAME`/`TURN_CREDENTIAL`;
  a GET credentials endpoint can be used via `TURN_CREDENTIALS_URL`.
* **Twilio Network Traversal Service** — creates ephemeral tokens with
  `POST /2010-04-01/Accounts/<AccountSid>/Tokens` (Basic auth with account SID +
  auth token, `Ttl` parameter) and returns an `ice_servers` array. Our parser
  accepts that shape, but Twilio expects form-encoded parameters, so use a small
  server-side proxy (or accept the default 24 h TTL) if you point
  `TURN_CREDENTIALS_URL` at it. Twilio NTS is a paid product with trial credit.

### C. Static credentials (least secure)

`TURN_USERNAME` + `TURN_CREDENTIAL` work with any managed relay, but the password
is delivered to every authorized browser and cannot be rotated per session.
Use only as a fallback.

### Verification mode

`ICE_TRANSPORT_POLICY=relay` forces every candidate through TURN. With no usable
relay the ICE endpoint returns **503 `TURN_MISCONFIGURED`** and the client refuses
to start (no peer connection, no microphone capture) instead of showing a silent
STUN-only call. Do not leave relay-only enabled in production unless the relay is
confirmed working.

## 5. What still requires an external action

1. Create the relay: a coturn VPS **or** a Cloudflare/Metered/Twilio account.
2. Put its URL + secret/credentials (or provider URL + token) into the Render
   environment. Never commit them.
3. Confirm `/api/health` shows `ice.configured: true` and the credential mode.
4. On two real devices, open the diagnostics panel and confirm relay candidates
   and `media flowing: yes (RTP received)` in both directions. Only then is TURN
   verified; the automated tests use mocks and cannot prove relay media.

## 6. AI session lifecycle deployment notes

The AI recovery fix does **not** add or rename environment variables. Keep the
existing `ULTRAVOX_API_KEY` (server-side only). No TURN change is involved.

A redeploy of this branch is required for the fix to take effect. After the
deploy:

1. `GET /api/health` should still report `ai.ready: true`. This only means the
   server can create calls — it is not proof of a live session.
2. On `/sales`, the **AI copilot status** panel (and header chip) must move
   through *Creating AI session → Connecting AI → AI connected* only when the
   customer device actually reports a live Ultravox session.
3. Server logs contain `[ai] ...` lines for failures and superseded-call cleanup.
   They never contain the API key, a join URL, or a token.
4. Ultravox calls are capped at `maxDuration: 3600s`. When a call ends, the
   customer device creates a new one (bounded to 3 automatic attempts); the
   salesperson can press **Restart AI** to force another fresh call without
   interrupting the human audio call.


## 7. Dashboard split and salesperson captions

No new environment variable and no new dependency is required for the separated
dashboards or the customer-facing transcript.

* The transcript of the salesperson's speech uses the browser Speech Recognition
  API on the **salesperson** device. That API requires a secure context
  (`https://` or `localhost`) and a Chromium-based browser. Firefox has no
  implementation; the salesperson dashboard then shows "unavailable in this
  browser" and the customer is told captions are unavailable. The human call is
  unaffected.
* Because captions are produced in the browser, no audio is uploaded anywhere
  for them. Only text is relayed through the existing authenticated WebSocket.
* The customer interface no longer renders AI suggestions, AI status or
  diagnostics. This is enforced by the server (role-scoped hydration and
  message routing) as well as by the customer view model; check it on a real
  device by confirming the customer page shows only call controls, connection
  state and the salesperson transcript.
