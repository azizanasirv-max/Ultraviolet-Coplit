# Render deployment and TURN setup

## 1. Why Render failed before

### `sh: 1: vite: not found`

The repository had **no `package-lock.json`** (only a `bun.lock`). Render detects
npm projects by `package-lock.json`/`yarn.lock`; without one it ran the build
command against an empty `node_modules`. The build tool was not missing from
`package.json` — dependency installation never happened.

Fixed by committing `package-lock.json` (generated by npm) and using an explicit
build command that always installs the locked tree.

### `ERESOLVE` (esbuild conflict)

The repository declared **`esbuild@^0.25.0` directly in `devDependencies`** while
`vite@8.3.5` declares an optional peer dependency `esbuild: ^0.27.0 || ^0.28.0`.
npm 7+ installs peer dependencies and refuses to resolve two incompatible
`esbuild` majors. The direct dependency was unused (nothing imports `esbuild`;
`tsx` and Vite bundle their own), so it was **removed** rather than suppressed
with `--force`/`--legacy-peer-deps`. npm now resolves `esbuild@0.28.2` for Vite.

### A third, latent failure: `tsx` in devDependencies

`npm start` runs `tsx server.ts`, but `tsx` was a devDependency. Any
production install (`NODE_ENV=production`, `--omit=dev`) would have started the
server and failed with `tsx: not found`. `tsx` is now a **runtime dependency**.
Vite is also kept in `dependencies` so the build works even on a host that
installs only production dependencies; the server imports Vite **dynamically and
only when `NODE_ENV !== 'production'`**, so production never loads it.

The Bun workaround (`bun install --frozen-lockfile && bun run build`) was **not**
used: the lockfile was removed in favour of npm, and Render's default Node
runtime does not provide Bun.

## 4. TURN: what exists and what you must create

**No TURN service or credential is configured in this repository.** Code cannot
create a relay; a relay must run somewhere with public UDP/TCP ingress. Render
web services only expose HTTP(S), so coturn must run on a VPS/other host (or use
a managed provider).

Six supported modes, in order of preference:

### A. coturn with a shared secret (recommended, short-lived, self-hosted)

1. Run coturn on a small VPS with a public IP and open UDP/TCP 3478 (and 5349
   for `turns:`), configured with `use-auth-secret` and a long random `static-auth-secret`.
2. In Render set:
   * `TURN_URLS=turn:<host>:3478?transport=udp,turns:<host>:5349?transport=tcp`
   * `TURN_SECRET=<the same static-auth-secret>`
3. No long-lived TURN password ever reaches a browser: the server derives
   `username=<expiry>:<sessionId>` and `credential=base64(HMAC-SHA1(secret, username))`.

This is the only mode that has been exercised end-to-end by this repository's
HTTP/signaling tests (with mocked relay reachability). Real relay media still
requires the VPS + credentials above.

### B. Managed provider with a credentials API

Set `TURN_CREDENTIALS_URL`, `TURN_CREDENTIALS_AUTH` and, if the provider requires
it, `TURN_CREDENTIALS_METHOD=POST`. The server fetches and caches temporary ICE
servers for 5 minutes; the provider API key stays server-side.

* **Cloudflare Realtime TURN** — official docs: the TURN service is free when
  used with the Realtime SFU, otherwise **$0.05 per real-time GB** outbound to the
  TURN client. Credentials are created with
  `POST https://rtc.live.cloudflare.com/v1/turn/keys/<KEY_ID>/credentials/generate`,
  `Authorization: Bearer <TURN_KEY_API_TOKEN>`, body `{"ttl": <seconds>}`, and the
  response is `{ "iceServers": [ ... ] }`. This matches our `POST` mode. You need
  a Cloudflare account, a TURN key, and its API token.
* **Metered TURN** — the free plan is a **500 MB/month trial** (ingress+egress);
  paid tiers start at 150 GB/$99 per month. Its REST API issues/reads credentials
  (the v2 credentials *list* endpoint reports “api not available under free
  plan”, so use the credential-creation endpoint or dashboard credentials).
  Static project credentials can be placed in `TURN_USERNAME`/`TURN_CREDENTIAL`;
  a GET credentials endpoint can be used via `TURN_CREDENTIALS_URL`.
* **Twilio Network Traversal Service** — creates ephemeral tokens with
  `POST /2010-04-01/Accounts/<AccountSid>/Tokens` (Basic auth with account SID +
  auth token, `Ttl` parameter) and returns an `ice_servers` array. Our parser
  accepts that shape, but Twilio expects form-encoded parameters, so use a small
  server-side proxy (or accept the default 24 h TTL) if you point
  `TURN_CREDENTIALS_URL` at it. Twilio NTS is a paid product with trial credit.

### C. rstream managed STUN/TURN (temporary credentials)

rstream's Control plane API issues short-lived, project-scoped TURN credentials.
The server requests them on demand from the already-authenticated
`GET /api/sessions/:id/ice-config` endpoint; the browser only ever receives the
temporary `username`/`credential`, never the rstream token.

Verified contract (checked 2026-10 against
<https://rstream.io/docs/integrations/stun-turn>,
<https://rstream.io/docs/integrations/apis> and
<https://rstream.io/api/openapi.json>):

```
POST https://rstream.io/api/projects/tunnels/<project-id>/turn-server/credentials
POST https://rstream.io/api/projects/tunnels/resolve/<project-endpoint>/turn-server/credentials
  Authorization: Bearer <rstream access token>
  Content-Type:  application/json
  Body:          { "ttlSeconds": 600 }        # integer 1-3600, default 600
  200:           { "username": "...", "credential": "...", "urls": ["turn:..."], "ttl": 600 }
  Errors:        400 401 403 404 409 429 503   (Cache-Control: no-store)
  Required rule: turn.credentials.create + access to the project
```

Behaviour implemented in `server/turn.ts`:

* `RSTREAM_AUTHENTICATION_TOKEN` is used as the bearer token and stays
  server-side. It is never returned, logged, or embedded in error messages.
* `RSTREAM_PROJECT_ENDPOINT` (preferred) or `RSTREAM_PROJECT_ID` selects the
  project; the request uses `POST` with `{"ttlSeconds": N}`.
* The requested TTL is clamped to rstream's 1-3600 second range
  (`TURN_TTL_SECONDS`, default 3600 → 3600).
* Responses are validated (`username`, `credential`, at least one `turn:`/
  `turns:` URL, `ttl`); malformed payloads are rejected, never partially used.
* Credentials are cached per process until ~1 minute before expiry and are
  **never** served after `expiresAt`; a 5 s request timeout bounds the call.
* Provider failures map to actionable, secret-free messages (e.g. rotate the
  token on 401, missing `turn.credentials.create` on 403, verify the project on
  404) and surface as warnings for `ICE_TRANSPORT_POLICY=all`. With
  `ICE_TRANSPORT_POLICY=relay` they fail closed with **503
  `TURN_MISCONFIGURED`**.
* If `TURN_URLS` + `TURN_SECRET` (or static credentials) are also configured,
  rstream takes precedence when healthy and the static relay is **preserved as a
  fallback** when rstream is unreachable.

Render setup:

1. In the rstream dashboard, copy the project endpoint (and/or project id) and
   create an access token with `turn.credentials.create` plus access to that
   project.
2. Add the environment variables in the Render dashboard (they are declared
   `sync: false` in `render.yaml`, so nothing is stored in the repo):
   * `RSTREAM_AUTHENTICATION_TOKEN` — the access token (secret).
   * `RSTREAM_PROJECT_ENDPOINT` — the project endpoint, **or**
     `RSTREAM_PROJECT_ID` — the project id.
   * optional `RSTREAM_API_BASE_URL` — only for a self-hosted/alternate control
     plane; defaults to `https://rstream.io`.
3. Leave `TURN_URLS` unset unless you want the static fallback.
4. After redeploy, `GET /api/health` reports
   `ice.credentialMode: "provider"` without exposing any URL, token or
   credential. Real relay media must still be confirmed on two devices.

#### Static rstream JSON credentials (temporary testing, no API token)

For short-lived testing you can paste the `username` / `credential` / `urls`
values from an rstream TURN JSON response directly into the Render environment:

* `RSTREAM_TURN_USERNAME` — the JSON `username`
* `RSTREAM_TURN_CREDENTIAL` — the JSON `credential`
* `RSTREAM_TURN_URLS` — the JSON `urls`, comma-separated
  (`turn:host:3478?transport=udp,turns:host:5349?transport=tcp`)
* `RSTREAM_TURN_TTL_SECONDS` — how long you declare them valid (default `600`,
  clamped to 1–3600; rstream issues at most one hour)

This mode needs **no** `RSTREAM_AUTHENTICATION_TOKEN` and **no** project
identifier. It is used when the API-based flow above is not configured; if both
are configured, the API flow wins and these static values act as its fallback.

> **These credentials expire and are NOT renewed automatically.** The server
> cannot mint new ones without the API flow, and it does not claim otherwise.
> The TTL window starts when the process first serves the credential. Once
> `RSTREAM_TURN_TTL_SECONDS` has elapsed, the credential is withheld from ICE
> responses, `/api/health` reports `hasErrors: true`, and relay-only mode returns
> 503. To recover, obtain a fresh JSON credential from rstream, update
> `RSTREAM_TURN_USERNAME` / `RSTREAM_TURN_CREDENTIAL` / `RSTREAM_TURN_URLS` in
> Render, and redeploy (or restart) so the new values are loaded. A new value
> starts a new window; the same value is never extended.
>
> The window is tracked per process because rstream does not expose the original
> issuance time to us: a restart (including a Render spin-down/wake-up) re-anchors
> it. That does not make an older credential valid — if rstream already expired
> it, allocations fail immediately. Always paste fresh values before testing and
> replace them manually as they age.

Static values are shown to authorized browsers by design (they are the ICE
credential). They are never written to logs or `/api/health`, and no API token is
involved in this mode.

### D. Static credentials (least secure)

`TURN_USERNAME` + `TURN_CREDENTIAL` work with any managed relay, but the password
is delivered to every authorized browser and cannot be rotated per session.
Use only as a fallback.

### E. ExpressTURN free tier (operator-entered, temporary testing)

The ExpressTURN **free** plan provides a TURN server URL, a username and a
password. It does **not** provide a Secret Key — ExpressTURN's shared-secret
authentication (`static-auth-secret` / HMAC credentials) is a **Premium-only**
feature, as stated on <https://www.expressturn.com/> ("the shared secret
authentication method is available only to Premium customers"). Free-tier
credentials therefore use the standard TURN long-term credential mechanism
(`lt-cred-mech`), which is exactly what a browser's `RTCIceServer`
`username`/`credential` uses.

Do not invent or derive credentials: this implementation has no HMAC path. The
three values you enter are placed into the ICE configuration unchanged.

Setup (browser only; no environment variable):

1. Deploy the service (no persistent disk, database, Render Shell or ExpressTURN
   Secret Key involved).
2. Open the app's **Admin Settings** section (button in the top bar of `/` or
   `/sales`), or `https://<service>/admin/turn` — both drive the same backend.
   The first visit shows **First-time setup**. Create a setup password:
   * at least 12 characters, using at least three of lowercase, uppercase,
     numbers and symbols;
   * the server stores only a salted **scrypt** hash (N=16384, r=8, p=1) in
     process memory — the plaintext is never stored, logged or rendered;
   * completing this claims setup. From then on the page requires that
     password and `/api/admin/setup` returns `409 SETUP_ALREADY_CLAIMED`, so an
     anonymous visitor cannot reset or take over the setup.
3. You are signed in. Enter:
   * **TURN server URL / address** — e.g. `turn:free.expressturn.com:3478`
     (a bare `free.expressturn.com:3478` is accepted and normalized to `turn:`).
     Multiple URLs can be comma-separated, e.g. add
     `turn:free.expressturn.com:3478?transport=tcp` for a TCP fallback.
   * **TURN username** and **TURN password** — copied verbatim from the
     ExpressTURN dashboard.
4. Make a call. `GET /api/health` reports `ice.configured: true`,
   `ice.credentialMode: "static"` and `ice.provider: "expressturn"`.

No `ADMIN_PASSWORD` (or any other environment variable) is required. If an
older deployment still defines `ADMIN_PASSWORD`, it is ignored and can be removed.

**Is the deployed service running this flow?** Two credential-free checks:

* `curl -s https://<service>/admin/turn | grep 'First-time setup'` returns the
  setup form (no environment variable involved). A redirect or 404 means an
  older build is deployed.
* `curl -s -o /dev/null -w '%{http_code}' https://<service>/api/admin/turn-settings`
  returns `401`; `.../api/health` shows only `ice.configured` /
  `ice.credentialMode` (never a username or credential).

**Restart / redeploy — safely reclaiming setup.** The setup-password hash and
the ExpressTURN credentials live only in this server process's memory. A restart
or redeploy clears both, and old admin session cookies stop working (the
signing key is regenerated per process). The page returns to first-time setup;
reclaim it by creating a new setup password and re-entering the ExpressTURN
values. No old credential is exposed during this: it no longer exists on the
server. Because a fresh process has no stored setup password, the **first
visitor** can claim first-time setup — complete the claim immediately after
every deploy/restart. Closing that window completely would require persistence
(a database/disk) or an environment variable, both explicitly out of scope for
this flow.

Security properties:

* Setup and login attempts are rate-limited per client IP (8 attempts per 10
  minutes). Passwords are compared against the scrypt hash in constant time.
* Sessions are 2-hour `HttpOnly`, `SameSite=Strict` cookies signed with a random
  per-process key; they cannot outlive a restart.
* Every state-changing admin request must be same-origin (the Origin/Referer
  host must match the request host, `X-Forwarded-Host` or `APP_URL`), sent as
  `application/json`, and carry the per-session `X-CSRF-Token` value. A stolen
  session cookie alone is not accepted.
* The admin page and status API never render or return the TURN username, TURN
  password, setup password or password hash after saving. Status is limited to
  `configured`, `urlCount`, `updatedAt`, `storage: "memory"`, the safe setup
  claim flag and the session's CSRF token. The TURN password is never returned
  by any API, log or error message.
* Authorized session participants receive the credentials only through the
  existing authenticated ICE endpoint (`GET /api/sessions/:id/ice-config`);
  anonymous and cross-session callers get 401. WebRTC signaling, call recovery
  and salesperson/customer role isolation are unchanged.

Precedence when several TURN sources are configured:
`ExpressTURN` (admin page, memory) → rstream API → generic
`TURN_CREDENTIALS_URL` → coturn/static `TURN_URLS`. Existing rstream values may
remain set but are unused while ExpressTURN credentials are present.

### Verification mode

`ICE_TRANSPORT_POLICY=relay` forces every candidate through TURN. With no usable
relay the ICE endpoint returns **503 `TURN_MISCONFIGURED`** and the client refuses
to start (no peer connection, no microphone capture) instead of showing a silent
STUN-only call. Do not leave relay-only enabled in production unless the relay is
confirmed working.

### Diagnosing a real connection failure

Work from the server outward; do not assume TURN is the cause:

1. `GET /api/health` → `ice.configured`, `ice.credentialMode`, `ice.provider` and
   `ice.warnings`. `configured: false` means the running process currently has no
   usable relay (for example: the ExpressTURN values were entered at
   `/admin/turn` before a restart, and process memory was cleared).
2. `GET /api/sessions/:id/ice-config` as a participant → confirm the response is
   JSON (not an HTML error page), `hasTurn`, and exactly the expected
   `iceServers` entries. A 401/404 means the credential or session is wrong or
   the server restarted; a 503 means relay-only with no relay.
3. Salesperson dashboard → Details → `pcState`, `iceState`, candidate counts,
   `selected pair` and `bytes sent/received`. `relay candidates 0` with
   `policy relay` means the TURN host is unreachable or rejected the credentials.
4. Browser devtools console for the salesperson page shows the engine log
   (`ICE configuration attempt …`, `addIceCandidate failed`, etc.). The customer
   page never shows these.
5. `audio flow` reads `both` during a call. `outbound-only` means the peer is not
   hearing this device; `inbound-only` means this device is not hearing the peer;
   `none` with `pc connected` means no media path (typically no TURN). The engine
   also logs `Peer connection is connected but no audio has arrived ...` and
   starts a bounded ICE restart on its own after 8 s without any inbound RTP
   (20 s if audio had been flowing and stopped). It never restarts ICE because a
   background tab was throttled.
6. Server log: `[ice]` lines for provider/rstream failures and unexpected ICE
   build errors (which now return a JSON 500 instead of crashing the process).

Only relay candidates from a *confirmed working* TURN server prove the relay is
configured correctly; STUN-only success proves nothing about mobile/CGNAT peers.

## 7. Ultravox multi-key rotation and quota-aware failover (Task 4)

### Provider error semantics consulted (2026-10)

Sources:

* <https://docs.ultravox.ai/api-reference/introduction.md> (API overview,
  `X-API-Key`, rate-limit tables)
* <https://docs.ultravox.ai/gettingstarted/concurrency.md> (429/503 semantics,
  `Retry-After`, concurrency)
* <https://docs.ultravox.ai/gettingstarted/faq.md> (30 free minutes per account)
* <https://api.ultravox.ai/api/schema/> (OpenAPI schema; used to confirm that
  Create Call documents no idempotency key and no error-body schema)

What the provider actually documents:

* Authentication is `X-API-Key`; keys are 41 characters (`8` + `.` + `32`) and
  must never be exposed to client code.
* API request limits apply at **both account level (500 req/s) and API-key level
  (200 req/s)**.
* Call-creation limits are plan/account scoped: Free/PAYGO 5/s and 30/min; Pro
  10/s and 120/min.
* Call concurrency is account scoped: Free/PAYGO has a hard cap of 5 concurrent
  calls; paid plans have no hard cap but can still return 429 under load.
* A 429 can mean account concurrency, call-creation limiting or general load. It
  is **not** evidence that an individual key's quota is exhausted.
* 503 is used when the provider cannot create a call (for example priority
  capacity), and `Retry-After` is documented for 429 **and** 503 (seconds or an
  HTTP date).
* 401 means missing/invalid API key; 403 means insufficient authorization. They
  are separate from 429.
* Create Call has **no documented idempotency key**, so the outcome of a
  timed-out/network-failed POST is ambiguous.
* The free allowance is **account-wide** (30 free minutes). No documented
  endpoint exposes "remaining quota per key"; the call-usage endpoint is
  aggregate historical usage, not a remaining-quota/reset API.

**Consequence:** multiple keys only add independent capacity when they belong
to **separate Ultravox accounts/projects**. Keys generated inside one account
share its concurrency, call-creation and quota limits. The server still rotates
on quota/rate evidence within a finite budget, but it does not claim that this
bypasses an account-wide limit.

### Configuration

Preferred (Render dashboard → Environment → `ULTRAVOX_API_KEYS`, `sync: false`):

```json
[{"id":"primary","key":"<key 1>"},{"id":"backup","key":"<key 2>"}]
```

Compact list form is also accepted:

```text
primary=<key 1>,backup=<key 2>
```

Rules (also in `.env.example`):

* ids are non-secret, unique, 1–32 chars of `A-Z a-z 0-9 . _ -`; generated ids
  (`key-1`, `key-2`) are ordinal, never derived from key material;
* keys are trimmed; empty, placeholder (`MY_...`, `CHANGEME`, `<...>`),
  duplicate, whitespace-containing and over-long entries are rejected;
* at most 10 keys are read;
* `ULTRAVOX_API_KEYS` takes precedence when it yields at least one valid key;
  the legacy `ULTRAVOX_API_KEY` is then ignored with a warning;
* if `ULTRAVOX_API_KEYS` is present but invalid/empty, a valid legacy
  `ULTRAVOX_API_KEY` is used as a safe fallback (warning), so a typo does not
  silently disable the AI;
* with neither variable (or only a placeholder) the app still serves all human
  audio and returns `503 MISSING_API_KEY` / `ULTRAVOX_KEY_CONFIG_INVALID`.

Keys are read only by the Node server. They are never embedded in Vite output,
API responses, join URLs, transcript messages, logs or diagnostics. Only the
non-secret id is used in operator output.


### Rotation rules

| Provider result | Category | Action | Key state |
| --- | --- | --- | --- |
| 200 with valid call payload | none | stop | success timestamp only |
| 402 | quota exhausted | rotate (if budget left) | quota cooldown (reset hint or 1 h fallback) |
| 403 with explicit quota/billing wording | quota exhausted | rotate | quota cooldown |
| 403 otherwise | permission | **fail, no cycling** | unchanged |
| 429 with explicit quota/billing wording | quota exhausted | rotate | quota cooldown |
| 429 with account/concurrency/plan wording | rate limited | **wait** (no rotation) | rate cooldown from `Retry-After` |
| 429 with key-level wording or no scope evidence | rate limited | rotate within budget | rate cooldown from `Retry-After` |
| 401 | authentication | **fail, no cycling** | short auth/diagnostic cooldown |
| 400/404/409/413/415/422 | invalid request | **fail, no retry** | unchanged |
| 408/5xx/network error on Create Call | transient | **fail** (ambiguous; no retry) | unchanged |
| any unclassified status | unknown | **fail** | unchanged |

Bounded retry policy:

* the attempt budget per logical Create Call is
  `min(configured keys, ULTRAVOX_MAX_KEY_ATTEMPTS)` (default 3, hard max 5);
* a key can appear at most once in one operation;
* no rotation or retry on authentication, permission, validation, unknown or
  transient failures;
* the server never sleeps inside the AI-call HTTP request. A documented
  `Retry-After` is returned as `retryAfterSeconds`; the existing client recovery
  loop remains bounded to 3 attempts;
* POST /calls is non-idempotent. A network failure/5xx is reported with
  `ambiguous: true` and the key is **not** marked exhausted, because a retry
  could create a second live AI session. The classification module does support
  `retry_same_key` for genuinely idempotent operations (for example DELETE), but
  Create Call does not use it.

`Retry-After` is capped at 5 minutes for a rate-limit cooldown; the quota
fallback is 1 hour with a 24-hour hard maximum. All cooldowns expire by time and
are then reconsidered deterministically in configuration order.

### Security and concurrency safeguards

* Raw keys exist only in process memory and the outbound `X-API-Key` header.
  Provider error bodies are read for classification only and are never logged
  or returned. The old `details` field was removed from the AI-call error.
* Diagnostics contain config **counts**, non-secret ids, health
  (`eligible` / `cooling_down` / `quota_exhausted` / `authentication_failed`),
  cooldown expiry, last category/reason and the last operation summary.
* The diagnostics endpoint remains salesperson-authenticated. `/api/health` only
  exposes `ready`, `keyCount`, `keySource` and the legacy `hasUltravoxKey`.
* Key state mutations are synchronous; cooldown deadlines use `Math.max`, so
  concurrent failures can only extend (never shorten) another request's
  evidence. A success does not clear a cooldown another in-flight request just
  recorded. Only time expiry makes a key eligible again.
* Selection is deterministic config order with an explicit exclude set. There is
  no random jitter loop and no unbounded retry.
* Existing live calls are reused without key selection. A `replace: true`
  request clears the old record first; the new call stores only the non-secret
  `apiKeyId` used. If creation fails, no join URL is cached and the human WebRTC
  path is untouched.


### Operator diagnosis

1. `GET /api/health` → `ai.ready`, `ai.keyCount`, `ai.keySource`. Readiness only
   means at least one valid key is configured; it is not proof of a live call.
2. Salesperson `GET /api/sessions/:id/diagnostics` → `ultravoxKeys` with:
   `configuredCount`, `eligibleCount`, `coolingDownCount`,
   `quotaExhaustedCount`, `authenticationFailedCount`, `maxAttempts`,
   `configErrors`, `configWarnings`, `lastOperation` (including
  `finalCategory`, `finalAction`, `failover`, `allKeysExhausted`) and per-key
  health/id.
3. Server logs use safe lines such as
   `[ai] Ultravox attempt key=primary status=429 category=quota_exhausted
   action=rotate reason=http-429-quota-evidence attempt=1/2`.
   Startup logs `[ai] Ultravox keys: N configured key(s), source=multi,
   attempt budget=N` and key-free `[ai] KEY CONFIG: ...` errors.

Common diagnosis:

* `ULTRAVOX_KEY_CONFIG_INVALID` → `ultravoxKeys.configErrors` names the entry
  number/id and the rule; no key material appears.
* `ULTRAVOX_AUTH_FAILED` → one key was rejected with 401. The pool does not try
  the other keys because that would hide a credential problem. Verify the key
  in the Ultravox console, then redeploy.
* `ULTRAVOX_QUOTA_EXHAUSTED` / `ULTRAVOX_KEYS_EXHAUSTED` → keys are cooling
  down; `availableInSeconds`/`retryAfterSeconds` show the bounded wait.
* `ULTRAVOX_RATE_LIMITED` with an `accountScoped` reason in logs → likely
  account concurrency/call-creation limit; another key in the same account will
  not help.

### Deployment limitations

* Key state is **in-memory and per process**. Render restart, spin-down or
  redeploy clears cooldowns; a second instance would have independent state. No
  Redis/database is used for this demo.
* The provider does not document per-key quota remaining/reset semantics. The
  implementation treats body/`Retry-After` reset hints as evidence, not truth.
* Keys in the same account share quotas/concurrency; rotation cannot bypass an
  account-wide limit.
* No live provider quota/429 scenario was exercised. Tests use mocked responses
  and a fake clock; they do not prove real quota behaviour.
